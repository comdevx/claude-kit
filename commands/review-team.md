description: Parallel code review and security vulnerability scanning with 5 specialized agents
---

You are the Review Team orchestrator. Launch 5 specialized review agents in parallel and aggregate their findings into a unified security and quality report.

## Step 1 — Determine Scope

Parse the argument provided (if any):

- **No argument or `changed`** (default): Get files from `git diff --name-only HEAD` and `git diff --cached --name-only`. If not a git repo, scan all source files.
- **`all`**: All source files in the project (exclude `node_modules/`, `.git/`, `vendor/`, `dist/`, `build/`, `.next/`, `__pycache__/`, `*.min.js`, `*.map`)
- **`<path>`**: The specific file or directory provided
- **`<branch>`**: Run `git diff <branch> --name-only` to get changed files

Collect the list of files in scope. If the list is empty, inform the user and stop.

Also check for a CLAUDE.md file in the project root and include its content as context for agents.

## Step 2 — Launch 5 Agents in Parallel

Launch all 5 agents simultaneously. Pass each agent:
1. The list of files in scope (or the scope description)
2. The project root path
3. Any relevant CLAUDE.md content
4. Clear instruction: "Review ONLY the files in scope. Report findings with confidence >= threshold."

**Agents to launch:**
1. **bug-hunter** — logic errors, race conditions, edge cases (confidence >= 80)
2. **security-auditor** — OWASP Top 10, injection, XSS, auth bypass (confidence >= 80)
3. **secret-scanner** — hardcoded secrets, API keys, credentials (confidence >= 70)
4. **dependency-auditor** — CVEs, outdated packages, supply chain risks (confidence >= 75)
5. **code-quality-reviewer** — anti-patterns, performance, error handling (confidence >= 80)

Wait for all 5 agents to complete before proceeding.

## Step 3 — Aggregate & Deduplicate

Process all findings:

1. **Deduplicate**: If 2+ agents flag the same file+line for similar reasons, merge into one finding
2. **Cross-validate**: If multiple agents flag the same issue independently, boost confidence by +5 to +10 and note "Confirmed by: [agent names]"
3. **Classify severity**:
   - **CRITICAL** (confidence 90-100): Fix immediately, high exploitability or data loss risk
   - **HIGH** (confidence 80-89): Fix before next release
   - **MEDIUM** (confidence 70-79): Fix soon, tracked issue
   - **INFO** (confidence < 70): Informational, low priority

## Step 5 — Localized Summary

Detect the machine's locale:
1. Run `defaults read -g AppleLocale 2>/dev/null` to get the locale (macOS)
2. If that fails or is empty, fall back to `echo $LANG`
3. Extract the language code: take the part before `_` or `.` (e.g., `th` from `th_TH` or `th_TH.UTF-8`)
4. If the language code is `en` or empty → **skip this step entirely**

If the language is non-English, output a concise summary section (10–15 lines max) written entirely in the detected language. Include:
- Issue count by severity (CRITICAL: X, HIGH: X, MEDIUM: X, INFO: X)
- 1–2 sentence overview of the most critical findings
- Top 3 recommended actions

Format the section as:

```
---

## [Summary heading in local language]

[Localized content here — 10–15 lines max, entirely in detected language]
```

## Step 6 — Auto-create Tasks from Findings

**Skip this entire step if CRITICAL + HIGH issue count = 0.**

Otherwise:

### 6a — Prepare task tracking files

Check if `docs/task.md` exists in the project root:
- If it does not exist: create the `docs/` and `docs/tasks/` directories, then create `docs/task.md` with this header:
  ```markdown
  # Task List

  | # | Task Title | Status | Ref |
  |---|------------|--------|-----|
  ```
- If it exists: read it to find the current highest task number (use that as the starting offset)

### 6b — Group CRITICAL and HIGH issues into tasks

Group related issues to avoid task sprawl:
- Issues in the **same file** → combine into one task
- Issues with the **same root cause** (e.g., all SQL injection, all missing auth checks) → combine into one task
- Unrelated issues → one task each
- **Cap at 10 tasks max**: if grouping still yields more than 10, combine the lowest-severity ones further

For each task group, write a task detail file at `docs/tasks/task-N.md` using this template:

```markdown
# Task N: [Descriptive title]

## Description
[What needs to be fixed — derived from the review findings]

## Context
- Detected by: Review Team — [agent name(s)]
- Severity: [CRITICAL / HIGH]
- Source file(s): [file:line references]

## Acceptance Criteria
- [ ] [Specific fix criterion 1]
- [ ] [Specific fix criterion 2]
- [ ] Verify no regression in related functionality

## Implementation Notes
- Key files to modify: [list from findings]
- Remediation: [paste from report]

## Testing Checklist
- [ ] Issue is no longer reproducible
- [ ] No new issues introduced

## Completion Notes
[To be filled when task is completed]
```

### 6c — Update docs/task.md

Append one row per new task:
```markdown
| N | [Task Title] | ⬜ | [detail](tasks/task-N.md) |
```

### 6d — Git commit/push (if applicable)

If the project is a git repo (`git rev-parse --git-dir` succeeds):
```
git add docs/task.md docs/tasks/task-N.md [... all new task files]
git commit -m "docs: add review-team tasks from security scan"
git push origin HEAD
```
Push failure is **non-fatal** — print a warning and continue.

### 6e — Print task creation summary

Print a table of all tasks created:

```
## Tasks Created

| Task # | Title | Severity | File(s) |
|--------|-------|----------|---------|
| N      | ...   | CRITICAL | ...     |
| N+1    | ...   | HIGH     | ...     |
```

## Notes

- If no issues are found by all agents: print "No issues found above confidence thresholds."
- If scope is a single file, agents should focus deeply on that file
- Agents have read-only access; they do NOT fix issues
- The dependency-auditor may run shell commands (`npm audit`, `pip audit`, etc.) if available
- **Step 5** outputs a localized summary only when the system locale is non-English
- **Step 6** auto-creates tasks only for CRITICAL and HIGH issues; MEDIUM and INFO issues appear in the report only
